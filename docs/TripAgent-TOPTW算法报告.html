1 · 一页看懂

TOPTW（Team Orienteering Problem with Time Windows，带时间窗的团队定向问题）回答的是：时间预算有限时，去哪些点、按什么顺序去，能让行程总价值最大。它与 TSP/VRP 的本质区别在于——TSP/VRP 要求访问全部节点、最小化成本；TOPTW 允许放弃部分节点（损失其利润），在时间预算内最大化选中节点的利润总和。这恰好就是行程规划的核心权衡：景点无穷多，一天只够去三四个。

TripAgent 用 OR-Tools RoutingModel 把「一天行程」建模成单车 TOPTW：利润函数编码「主选权重 + 景点评分 + LLM 顺位奖励 + 点级需求加成」，硬约束（营业时间窗、通行时间、当日上限）由求解器保证可行，软约束（建议游玩时段）以罚分形式参与优化。

M11 起本项目对 TOPTW 的用法有一次关键收敛：忠实执行模式（默认开）。求解池只含提案主选，主选以 10⁶ 利润锁定，求解器从「可以换点」退到「只排序 + 保证可行」——选点权完全收归提案层（LLM）。原因见第 7 章：求解器的优化目标（利润最大化、填满时间）会与用户的节奏意图（慢节奏/带老人/不要太累）直接打架，且优化器总会赢。换点能力保留为可回退配置（TOPTW_FAITHFUL_MODE=0）。

2 · TOPTW 问题原理

2.1 从定向越野说起

OP（Orienteering Problem）的名字来自定向越野：选手从起点出发、在关门时间前到达终点，途中经过若干检查点各得相应分数，如何选点与排序使得分最大。形式化定义：

N 个候选点，每点利润 Sᵢ、访问耗时 Tᵢ、时间窗 [eᵢ, lᵢ]
通行时间矩阵 C(i,j)
总预算 Tmax
max  Σ Sᵢ·xᵢ            （选中点的利润和）
s.t. 路径连通、连续；
     到达时刻 + Tᵢ ≤ 离开时刻，且落在 [eᵢ, lᵢ] 内
     总时长 ≤ Tmax

加「团队」（多辆车，K 条路径）即为 TOP；再加时间窗即为 TOPTW。该问题是 NP-hard 的——精确算法只适用于几十个点的规模，实用系统普遍采用构造启发式 + 元启发式改进。

2.2 与相邻问题的对照

问题目标节点访问时间窗典型解法
TSP最小化路径成本全部必访无2-opt / Concorde 精确
VRP最小化总成本全部必访可选（VRPTW）列生成 / 大邻域搜索
TOP / TOPTW最大化选中利润可选（弃点损失利润）TOPTW 必有构造 + GLS / 模拟退火

3 · 求解技术：OR-Tools 建模三要素

本项目使用 Google OR-Tools 的 RoutingModel，三个关键机制分别对应 TOPTW 的三个组成部分：

机制API在本项目中的用法
可选访问AddDisjunction([idx], penalty)每个候选点挂一个 disjunction；penalty = 该点利润——求解器访问它就赚利润、跳过它就损失利润，penalty 与绕路成本自动权衡。这是「选点」能力的来源；忠实模式下主选利润含 10⁶，等价于把主选变成必选
时间维度AddDimension(transit_cb, 0, horizon, fix_start=False, "time")transit 回调 = 上游游玩时长 + 通行分钟；节点 CumulVar 设硬范围 [开门, 闭店−游玩时长]（到达截止语义与 sequencer 对齐）；horizon = 当日跨度 − 120min 餐块缓冲（保底 240）；M15 夜间点放宽：池内最晚需求超出 horizon 时放宽至 min(当日域, 最晚需求+60)
软时间窗SetCumulVarSoftLowerBound / SoftUpperBoundbest_time 建议时段（morning/afternoon/evening/lunch）映射为软窗，偏差每分钟罚 5 分，并有 60 分钟封顶（见第 5 章）
实现细节：自环（未被访问的可选节点）transit 必须返回 0，否则时间维度不可行——这是 OR-Tools 建模的经典坑；另 RoutingIndexManager 的绑定参数顺序为 (num_nodes, num_vehicles, starts, ends)，传错会静默得到错误规模（本项目实证：传 (1, n, 0) 会得到 n 辆车、1 个节点）。

4 · 利润函数：把「产品语义」编码进目标

TOPTW 的落地质量几乎取决于利润函数怎么设计——它决定了求解器「认为什么重要」。TripAgent 的利润分五层：

profit(p) = 60 × rating               ← 平台评分（3~5 分制）
          + 15 × rank                 ← LLM 提案顺位（首点 rank 最大，逐位递减）
          + 600 × is_main             ← LLM 主选一次性加成
          + int(p["_bonus"] or 0)     ← 点级需求加成（如湖线点 +150）
          [+ 1,000,000 × is_forced]   ← 住宿锚点地标，不可舍弃
          [+ 1,000,000 × (is_main and lock_mains)]  ← 忠实执行模式：主选锁定

典型利润构成对比（rating=4 的主选 / 备选 / 必选锚点）

设计点取值理由
MAIN_BONUS600M3-1 参数扫描 300~1000 结果一致，取中位留余量——保证「任何一个主选 > 任何几个备选之和」，换点模式下求解器只会在时间不可行时才动主选
RATING_W60/分同分主选之间按评分定去留；两档评分差 120 分 < 600，不会翻越主选边界
RANK_BONUS15/名同为主选时保持 LLM 顺序（相似度目标）；参照 Google 可配置行程生成论文的同型设计
_bonus点级，如 150贯穿性偏好（湖线点）加成：量级取主选加成 1/4——够扭转两个主选之间的取舍，不干预主选 vs 备选的 600 级格局。必须 int：AddDisjunction 罚分要求 int64，float 直接 TypeError
forced / lock_mains+10⁶住宿锚点地标 / 忠实模式下的全部主选；舍弃代价远超任何组合收益，但时间可行性仍由硬窗保证——必选点排不下会暴露为违规/剔除记录，而非被静默丢弃
点级 _bonus 由调用方在候选池上以 dict(p, _bonus=…) 塞入——dict 拷贝，不污染 all_pois；否则同一 POI 被多天复用时加成会串味。

5 · 时间约束体系：硬窗、软窗、封顶与跨零点

这是本项目迭代最多的部分，共五层，由硬到软：

层机制语义
① 当日域horizon = max(240, 当日跨度 − 120min)排序器会在日中插午餐+晚餐各 1h，求解预算预扣餐块缓冲（M6），防止过度打包后整体后移溢出
② 营业硬窗CumulVar.SetRange(开门, 闭店−时长)到达 + 游玩 ≤ 闭店；窗口为空的点（闭店前玩不完）在建模前预剔除，防 CP Solver 直接 fail
③ 建议软窗SoftLowerBound / SoftUpperBound，5 分/分钟morning→12 点前、afternoon→13 点后、evening→17 点后、lunch→11~13:30（SLOT_WINDOWS）
④ 软窗封顶偏差 >60min 收紧硬域（SOFT_CAP_MIN）M3-2 关键修正：旧逻辑线性罚分无上限（晚到 5h 罚 1500 分），求解器「宁可晚到硬扛罚分」也不弃点——morning 点被拖到傍晚、时段空间白扔；封顶后要么贴时段排、要么干脆不排（弃利润）

⑥ 夜间点放宽 M15latest_end + LATE_POINT_MARGIN_MIN > horizon → horizon = max(horizon, min(当日域, latest_end+60))M15 新增：MEAL_BUFFER_MIN=120 把预算压到 630min（09:00→19:30），18:00 后开门的点（珠江夜游 19:00、宝业路宵夜街 18:00）结构性不可行 → 按池内最晚需求放宽，上限锁真实日窗；池中无晚间点时不触发，行为与旧版逐位一致。详见 5.2
冲突仲裁：软窗封顶与营业窗冲突时营业窗优先（能开就行）——约束的优先级是 硬可行性 > 时段偏好 > 利润。

5.1 跨零点归一化：为什么它是「上游一处，全库受益」（M14）

故障现象：广州宝业路宵夜街（18:00-02:00）与南京 1912 街区（17:00-02:00）自入库起从未能被排进任何行程。

根因：hhmm_to_h("02:00") = 2.0 而 day_start = 9.0，于是该点被三重判死：

① 预剔除（建模前）：  to_min(close) - dur = (2-9)*60 - 90 = -510  < 0        → 出池
② 时间窗（硬域）：    lo = to_min(open) = 540
                     hi = to_min(close) - dur = -510
                     lo(540) > hi(-510)  →  SetRange 得到空域
③ 排序器（sequencer）：任意 t 都满足 t + dur > close_h = 2.0  → 恒报「超出营业时间」

修法：在解析层统一归一（close_h ≤ open_h 时 +24），而不是在下游三处各打一个补丁。全库 722 点中仅 2 点触发，其余 720 点零影响。

放置位置改动面风险
下游逐处打补丁（预剔除 / 时间窗 / 排序器）3 处以上，且未来新增判据还要再补漏一处即复发；各层语义可能不一致
上游 parse_poi 归一（采用）1 处全库 2 点受影响，526 点零影响；所有下游自动一致
「死点」的判定特征（已固化为单测断言）：把 close_h 还原成 2.0（不归一）后，该点在求解结果里既不入选、也不出现在 dropped 列表——它从模型中完全消失。这与「利润权衡剔除」（进池、被弃、进 dropped）是两种截然不同的失败形态。scripts/test_cross_midnight_close.py 用 8 组断言把这两者区分固化下来。

注意：归一化解除的是「绝对不可排」，不等于「必然入选」。新入库的 KTV（闭店 06:00 → close_h 30.0）依赖归一化才排得进；同理宝业路宵夜街归一化后仍未落地，是因为提案层不提案它（召回层问题），与这里无关。

5.2 夜间点 horizon 放宽：预算预扣把「夜生活」判了死刑（M15）

故障现象：广州珠江夜游（19:00 开门）、宝业路宵夜街（18:00 开门）这类点位，即使跨零点归一化已修好、点位自身完全可行，也从不入选——且它不出现在 dropped 里，排查时极易误判为「提案层没提」。

根因：horizon = max(240, 当日跨度 − MEAL_BUFFER_MIN)，MEAL_BUFFER_MIN=120 → 当日跨度 750min（09:00→21:30）时 horizon = 630min（09:00→19:30）。19:00 开门的点 + 90min 时长 = 20:30 结束 > 19:30 → 结构性不可行。餐块预扣（M6）本意是防止过度打包后整体后移溢出，但它是全天一刀切的，没区分「这个点本来就在晚间」。

修法：新增 LATE_POINT_MARGIN_MIN = 60，建池后按池内最晚需求放宽：

latest_end = max( to_min(open_h) + dur*60  for p in candidates )
if latest_end + LATE_POINT_MARGIN_MIN > horizon:
    horizon = max(horizon, min(day_window, latest_end + LATE_POINT_MARGIN_MIN))

上限锁在真实日窗（day_window）之内，不会让预算越过营业日边界。对照实验（已固化为单测）：把 LATE_POINT_MARGIN_MIN 置负无穷即关闭放宽，同一构型下珠江夜游/宝业路「既不入选也不出现在 dropped」；修复后正常入选。

与编排层口径的差异（有意为之）：m2_planner._day_horizon（挪点容量预检）仍按 − MEAL_BUFFER_MIN 计算，不随夜间点放宽。这意味着「预检放行」比「求解能排」更严，属安全方向——不会出现「预检过了求解仍剔」的错配（报障 14 的口径纪律）。

7 · 忠实执行模式：TOPTW 角色的收敛（M11 · 默认开）

为什么要在求解层「主动削弱自己」？因为 TOPTW 的目标函数是「时间预算内利润最大化」——它天然倾向于把时间填满。而用户的节奏意图（「带老人」「不要太累」「慢节奏」）恰恰要求「不要填满」。当两者冲突时，优化器必然赢，因为它掌握着取舍权。这不是调参能解决的，是权利归属问题。

解法：把选点权整体交还提案层。参数 lock_mains=True 时：

for idx in 1..n:  AddDisjunction([idx], profit(node))

profit(p):
    pr = 60*rating + 15*rank
    if p in 主选:
        pr += 600
        if lock_mains: pr += 1_000_000      # ← 主选变成事实上的必选
    if p in forced: pr += 1_000_000
    pr += int(p["_bonus"] or 0)

配套的编排层变化：

环节换点模式（lock_mains=False）忠实执行（lock_mains=True）
池构造主选 + 邻域备选(半径 8km/8 个) + LLM alternatespool = list(mains)——只含主选
求解目标选点 + 排序只排序 + 保证可行
点数上限时间预算与利润函数决定落地 ≤ 提案
剔除原因口径「利润权衡」或「时间装不下」「时间预算内无法纳入（主选锁定仍装不下）」——只剩一种
补位池内换点 + _alt_substitute + LLM 兜底加点只走 _alt_substitute（净零换位，换出 N 个必须换进 N 个）
闭环阶段 3 _feedback_loop 参与跳过 _feedback_loop（不新增点）

同一提案在两种模式下的落地站点数（慢节奏天 vs 普通天）

实测收益：慢节奏天不再被堆到 5-7 站/20:47 收尾；剔除原因单一使前端文案可信；点数可预期。

代价与缓解：失去「库内自由发挥」对提案的补偿能力（若提案点全闭馆或全超时，忠实模式不会换点）。缓解手段把补偿前移到提案层——更完整的库内菜单注入、prompt 片区/招牌规则、以及「净零换位」在剔点后仍可同主题替换。

可回退：env TOPTW_FAITHFUL_MODE=0 / false / no / off，或 config.json toptw_faithful_mode: false。单测 scripts/test_faithful_mode.py（4 例）覆盖「池=主选 / 主选锁定 / 净零换位」。

8 · 编排层：TOPTW 在整条管线里的位置

单日求解器之上是 _solve_all_days 编排层，五项工程化设计：

设计实现收益
逐日建池忠实模式：pool = list(mains)；换点模式：主选 + LLM alternates（同天优先）+ 地理邻近召回，全局 used_backup 去重忠实模式下池规模 = 提案点数，求解更快且行为可预期
线程并行建池串行（维护去重状态）→ 线程池并行求解（≤4 并发）→ 串行合并OR-Tools 求解释放 GIL，多天耗时 ≈ 最慢单天
天复用（reuse）C 闭环/重平衡未触及的天直接复用上次有序解，不重解跨天调整只动少数天，全量重解是纯浪费
闭馆预剔除日期感知：当日闭馆的主选进池前剔除并记「求解器强制换点」主选闭馆信号进闭环 REVISE，而非求解器内部静默换点
酒店 depothotel 作为虚拟节点（全天开放、0 时长）置于 nodes[0]，每日强制出发返回首尾交通真实；无酒店时 depot 取主选第一点（M14 已修复：换位提前到 RoutingIndexManager 构造之前，见第 11 章）

容量预检与求解器同口径（M12 新增）：跨天重平衡在挪点前调用 _day_horizon(city)（= max(240, 日长分钟 − MEAL_BUFFER_MIN)）与 _day_load(ids, all_pois, mode)（dur 合计 + 按序列相邻腿时间累加，偏保守）。两者必须与 toptw.solve_day 的 horizon 口径完全一致，否则会出现「预检放行、TOPTW 仍剔」的错配（报障 14 根因）。M15 起有一处有意的不对称：夜间点放宽只作用于求解层 horizon，预检仍按 −120min 算，方向上更保守。

求解输出两样东西：有序访问序列（交给 sequencer 做时间轴与修复链）和被弃点列表（进入「为什么没去这些点」的用户可见解释 + 闭环信号）。被剔主选会触发两级补救：提案备选净零换位（同主题优先）→ LLM 兜底补点；需求主题彻底丢失时向用户出 ⚠️ 通知。

12 · 边界与演进方向

  • 单车模型：单日单路径符合旅游场景；若引入「上午/下午分组」需求，可扩展为 2 车 TOPTW（morning 组 + afternoon 组）。
  • 利润静态性：利润不随拥挤度/天气变化——拥堵与天气感知排入待办后，可作为时段相关的利润调整项注入。
  • 预算感知：门票价格（price 字段已回填）未进目标函数，可加预算约束维度（预算内利润最大化）。
  • 提前停止阈值：0.5% / 连续两次为经验值，可在更多城市样本上校准（当前单日 0.2~1.1s 已接近建池固定开销）。
  • 空档惩罚项：在目标中加入「行程内部大空档惩罚」以治理通用场景的时间轴空窗——需谨慎评估对求解时间与稳定性的影响。M15 已先做两步缓解：① 消除最大成因（餐厅被钉在餐窗整点，见编排层 MEAL_EARLY_TOL_H）；② 求解层不惩罚但如实披露（scan_gaps → _gap_notices）。
  • 召回层补强（让「能排但没被提案」的点可落地） ✅ M15 已修复：三层修复（确定性注入 → 必选与对账口径 → 目的地型餐饮豁免）后，宝业路宵夜街落地 18:00-19:30、莲花岛落地 11:26-13:26。忠实模式下求解器不再换点，提案层召回质量权重进一步上升，因此这条修在提案层与守门层而非求解器。
