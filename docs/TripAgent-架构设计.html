TripAgent 架构设计文档

AI 智能体驱动的多日行程规划系统 · 版本 M15（2026-09-15）· 对应代码 main@d25119e
一句话架构：LLM 负责它擅长的（用世界知识理解需求、选点、组织体验节奏），确定性系统负责它擅长的（落地校验、约束守护、组合优化）——世界知识主导选点，系统只做落地 + 约束 + 求解。LLM 从不直接决定最终行程；优化器从不用 LLM 修 bug。M11 起进一步明确：选点权完全收归提案层，TOPTW 只做「排序 + 保可行」。

1 · 设计哲学与边界划分

传统两种做法都有结构性缺陷：纯 LLM 排程（直接让大模型输出时间表）幻觉不可控、时间/里程约束靠"自觉"；纯算法规划（标签过滤 + 贪心）选点品味差、无法理解"带5岁孩子不要太累"这类软需求。TripAgent 的核心决策是把两者切在正确的层：

职责归属理由
需求理解、城市/天数/日期/酒店解析LLM（llm_extract/llm_clarify）+ 规则兜底自然语言歧义是 LLM 强项，规则只做降级
选什么点、去几个点（品味层 + 强度层）LLM 世界知识提案，不限制在库内清单；M11 起点数即承诺库内选点会让行程被 POI 库质量锁死（M1→M7 的演进动机）；节奏与强度是用户意图，不该由优化器改写
提案是否真实存在（事实层）确定性落地匹配（四级），绝不信 LLM幻觉结构性归零的关键：LLM 说什么不重要，库里能落地什么才重要
排程顺序、时间轴、里程/闭馆/用餐约束OR-Tools TOPTW 求解 + sequencer 确定性修复组合优化是求解器的领域，LLM 排时间表必然违规
被约束否决后的补救净零换位（确定性）+ 闭环反馈（LLM 重提案）+ 跨天重平衡（确定性局部搜索）各管各的：算法修"天间错位"与"同点置换"，LLM 修"选点被否决"
最终文案LLM 重生成，但只能基于最终时间轴防"标题有宋城、列表没有宋城"式文案漂移（ee9f1d2 教训）
推论：POI 库的角色从"选点来源"降级为"事实校验层 + 缺口探测器"——未落地清单就是库的质量报告，直接驱动扩库。

1.1 M11 忠实执行模式：为什么求解器要「放弃换点」

M7 时代求解器拥有换点权（池 = 主选 + 双源备选，按利润函数自由取舍）。上线后暴露一类目标冲突：用户说「带老人、不要太累」，提案层正确给出 3 点/天，但求解器站在"利润最大化"立场会把时间填满——优化目标与用户意图打架，且优化器赢。M11 的解法是把选点权整体交还提案层：

维度M7 换点模式M11 忠实执行（默认开）
求解池主选 + LLM alternates + 地理邻近召回池 = 主选（邻域备选/alts 均不进池）
主选利润+600+600 并额外 +10⁶（同 forced 口径，锁定必选）
点数上限由时间预算与利润函数决定落地 ≤ 提案（提案层承诺的点数）
剔除原因两种：利润权衡 / 时间装不下一种：时间预算真装不下（文案口径据此分流）
补位候选池换点 + _alt_substitute + LLM 兜底加点只走阶段 3 _alt_substitute（净零换位，不增站点数）
开关env TOPTW_FAITHFUL_MODE=0 或 config.json toptw_faithful_mode:false 可回退旧行为

代价：失去"库内自由发挥"对提案的补偿能力（提案点全闭馆/全超时则不换点）。收益：行为可解释、点数可控、节奏类需求不再被利润函数抹平。缓解手段是把补偿能力前移到提案层（更全的库内菜单注入 + prompt 片区规则）。

5 · 关键机制设计详解

5.1 四级落地匹配（防幻觉的核心）

提案里的每个名称按序通过四级匹配，任何一级命中即算落地；四级全失 → 记入 gaps 并写入缺口台账（不计入落地率惩罚，仅作库缺口信号）：

级别策略成本典型案例
L1 精确归一化后精确等值（去空格/全半角/括号注记）0「宋城·宋城千古情」→ HZ032
L2 分支变体剥除「东/西/北/乐园/度假区」等后缀生成变体再精确匹配0「上海迪士尼度假区」→「上海迪士尼」
L3 包含/模糊双向子串 + 编辑距离模糊（difflib≥0.62）0「外滩」→「外滩观景大道」
L4 LLM 辅助未落地清单 + 候选库打包给 LLM 对齐；住宿类库点双侧排除（防把酒店排进行程）1 次调用「武康路梧桐区」→ 武康路·安福路

实测：eval_m7 五城 10 组真实 LLM 提案落地率 10/10 全 100%，其中绝大多数命中 L1/L2——LLM 提案用的是官方名称，落地比想象容易。

5.2 TOPTW 利润函数（选点品味进入数学模型）

profit(p) = 60 × rating + 15 × rank + 600 × is_main + int(_bonus) [+ 10⁶ if forced or (lock_mains and is_main)]
主选奖励保证 LLM 主选优先保留；_bonus 承载点级需求加成（如湖线点 +150），必须为 int（OR-Tools 罚分要求 int64，float 会 TypeError）；忠实模式下主选再叠 10⁶ 变成事实上的必选。forced（住宿锚点地标）同样 10⁶，但时间可行性仍由硬窗保证——排不下会暴露为违规而非静默丢弃。

is_full_day（duration_h≥8，如迪士尼）自动独占一天；软时间窗偏差每 1 分钟罚 5 分并封顶 60 分钟（封顶后「要么贴时段排、要么不排」）。

5.3 闭环反馈（两个触发点，共享 2 轮预算）

触发点信号动作采纳守卫
① 落地不足gaps 非空 或 落地率 < 0.85未落地清单回传 REVISE 重提案修正确实减少未落地/剔除才采纳，否则保留原结果（防震荡）；MAX_REVISE_ROUNDS=2
② 主选被剔mains_dropped 非空（ee9f1d2 补上——此前只看修复链剔除，求解器剔主选从不触发，宋城案例暴露）剔除 POI + 原因回传。忠实模式下原因口径统一为「时间预算内无法纳入（主选锁定仍装不下）」
③ 片区重复相邻两天 <1.2km 点位对（_crossday_area_overlap）晚一天的点回传 REVISE 换到其他片区采纳条件 = 剔除 + 重复总数下降

备选被剔不算触发——备选本来就该被挑拣，闭环只救"LLM 的核心意图被系统否决"。确定性 gate 必须挂在循环的每一个入口：第一轮挂了、第二轮漏挂，等于没挂（报障 15 残余的教训）。

5.4 跨天重平衡（对标 Google《Optimizing LLM-based trip planning》stage-2）

  • 各日 TOPTW 独立求解后，确定性尝试把 POI 移动到地理更近的日簇（纯算法，0 次 LLM 调用）
  • 接受条件四选全：移动后全行程 0 违规 + 0 修复剔除 + 总里程改善 > 0.5km − 2km 相似度罚分（罚分尊重 LLM 初稿，不无意义搬运）
  • 挪点前容量预检（M12 新增）：_day_horizon(city) 与求解器同口径（日长 − 120min 餐块预扣，保底 240），_day_load(ids, all_pois, mode) 按序列累加 dur + 相邻腿时间（偏保守）。预检不过则不挪——否则预检放行、TOPTW 仍剔（报障 14 根因）
  • 保护规则：is_full_day 大点与 forced 锚点永不动；供出日至少保留 3 点（慢节奏）或 1 点；移动后整体重求解，主选掉点则整体回滚
  • 指标 n_day_moves 透出——机制只在有真实收益时动作

5.5 文案-时间轴一致性

compose 阶段 4 用 REGEN_PROMPT 对最终时间轴重新生成 theme + reason，prompt 明确约束"只能提到时间轴里实际存在的 POI"（举例：时间轴没有宋城就不能叫宋城怀古）。这是对"提案主题残留被剔 POI"问题的根治（ee9f1d2）；前端 Day 卡、分享 HTML、PNG 长图三处消费同一字段。排程事实（闭馆日）注入 prompt，与事实矛盾的 tips 被确定性剔除；reuse_days 集合内点位未变的天复用既有文案。

5.6 住宿锚点（三级匹配 + 开关化 + 防线）

用户说"住迪士尼附近"时：L0 库内地标匹配（rating≥4，"迪士尼"直接命中 SH006）→ L1 高德 POI 搜索（含"酒店"关键词过滤）→ L2 裸搜兜底。解析出的地标可注入当日必选（ensure_landmark_in_day_map + forced）；确定性硬保障做成默认关的开关。

凭空住宿锚点防线（M12 新增）：NL preflight 的 LLM 曾把行程范围描述（「都在太湖边」）误抽成 hotel:"太湖"，再被 L0 双向子串匹配命中「太湖西山岛」→ 凭空多出一个住宿锚点。修复为双层：① server 侧确定性防线——query 无「住|酒店|民宿|宾馆|客栈」字样时不采纳 nl.hotel（参数/正则/显式 hotel 不受影响）；② preflight prompt 收紧。教训：prompt 层单独不够（缓存回毒 + LLM 偶发仍抽），确定性防线是硬保障。

5.7 远郊大点片区守门 M9 · 求解前几何整理

动机（极地海洋公园案例）：提案把萧山远郊大点（距市中心 18.8km、5h）与城北片区（拱宸桥）混排同天，两片区相距 24km+，日里程必然超预算 → 修复链事后剔最远点 → 世界知识主选被误杀且需求主题丢失。教训：几何合理性应在求解前保证。

_far_big_point_regroup(day_map, all_pois, family) 确定性算法（0 LLM 成本）：
  • 大点识别：距市中心 >12km（FAR_BIG_KM）且时长 ≥4h（FAR_BIG_MIN_H）；
  • 错配判定：同天其他点与大点直线距离 >10km（FAR_BIG_SPREAD_KM）视为错配；
  • family 严格档：亲子查询下 5h ≤ dur < 8h 的远郊点（野生动物世界 5.5h / 海洋公园 5h 级）独占一日；
  • 环湖/海岛主题日豁免（M12 新增）：非 family 严格档时，若被判错配的点全部 >12km 远郊，视为「环湖/海岛主题日内部点位」——湖线点位天然相距十几公里，不拆。此条修复了「环湖骑行主题日被拆杀」（FAR_BIG_KM=12/SPREAD_KM=10 对环湖线否则恒失效）；
  • 移位目标：错配点移到「与该点平均距离最近的天」；目标天排除其他「需独占」的天（防互踢震荡）；最多 2 轮（FAR_REGROUP_PASSES）；
  • 降级路径：无法完全让位 → 不强行移动，记 far_big_solo 通知「建议把它单独安排一整天」。

5A · 性能工程（M8.5 · 23.3s → 12.9s / 缓存 8.3s）

瓶颈画像（探针 probe_perf.py，武汉 2 天基准）：LLM 4 次串行占 63%，TOPTW 跑满求解预算占 34%，跨天重平衡触发后全量重解是主要浪费。五项核心手段：

手段实现收益
天复用增量重解_solve_all_days(reuse=…)：跨天重平衡/C 闭环只重解点位变化的天，未变天直接复用上次解与文案闭环场景省一半求解

质量护栏：每批优化伴随离线回归 + 真实 LLM 端到端 0 违规；进度条五段式（澄清→提案→落地→求解→文案）+ 闭环轮次徽标，把等待变成可感知的过程。

5B · 慢节奏档（M12 · 节奏类需求的全链路宽松化）

触发：SLOW_PACE_RE = 老人|轮椅|行动不便|腿脚不便|慢节奏|悠闲|不累|太累|宽松。定义在 sequencer（排时层需要 slow 口径），m2_planner re-export——planner→sequencer 单向依赖，不能倒置成环。

⚠️ 正则陷阱（报障 9）：「不要太累」不含「不累」这个连续子串（中间隔了「要」「太」）→ 旧正则不匹配 → 慢节奏档整条链路被旁路。教训：慢节奏触发的亲子回归全是离线确定性路径，测不出 LLM 提案链的正则门控——正则改动必须用真实 LLM 实测验证。

prompt 层：每天 2-3 点不超 4、白天为主 17:30 前收尾、不排只有夜间才开放/运营的点、平缓无障碍点位、傍晚密度规则此档豁免。

确定性兜底七处（缺一即漏——evening 点/超员点即使被 prompt 禁止，仍会从 alt 补位/填空/换点/池捞回来）：

1主选层移除 evening + nightlife 点（用户明确要夜景则不过滤）
2_alt_substitute跳过夜间备选 + 补位 cap4（净零换位不得超员）

5提案层截断 stops ≤ 4（LLM 对「不超 4」遵循不足）
6补强池三重过滤：evening/nightlife + 徒步登山 tags + dist_center_km > 15

夜间点判据精准化（报障 11）：poi_db.is_night_only(p) = nightlife 类目 or open_h ≥ 16.5（NIGHT_OPEN_H）。不能按 best_time=evening 一刀切——外滩（0:00-23:59）/南京路步行街/陆家嘴滨江/山塘街全是全天开放点，sequencer 排时只看 open/close，排白天毫无障碍；误杀曾致上海亲子慢节奏 Day2/Day3 2 站 15:21/14:45 就收工。

餐窗保障配套：MEAL_LEAD_H=0.5（到达距饭点 ≤30min 先吃再逛，全档位通用）、游完就地补餐（非美食 POI 游览结束点恰在窗内则先吃再走）、MEAL_EXIT_GRACE_H=0.75 窗尾宽限 + MEAL_END_LEAD_H=1.5 收尾晚餐提前量。

机制盲区（已知遗留）：TOPTW 不惩罚行程内部空档——evening 软窗 + 点少的天会把时间轴拉出数小时空档（3.4h 实测）。慢节奏靠移除真夜间点规避；通用场景未治（动 solver 风险大）。

5C · 餐窗优先权与对账（M12 · 正餐保障链）

病灶：_build_timeline 单趟遍历中通用餐块先到先占窗（11:30 占掉午餐窗、17:00 占掉晚餐窗）→ 遍历到真实正餐 POI 时窗口已被占 → 落进另一窗或超 MAX_MEAL_WAIT_H → 违规剔除 → 前端「美食 POI 未能安排进用餐时段」。教训：候补块与真实 POI 之间必须有显式优先权——真实 POI 优先。

层机制作用
排序层_assign_food_windows(foods, city)统一分配餐窗：午市偏好优先、同窗顺延、不可用窗不分配；判据收紧为「关门晚于窗中点」

实测：修复后线上美食剔除 4 → 0；PROPOSE_PROMPT_VER 现值 v7（改提案 prompt 必递增，令 7 天缓存失效）。

5E · 跨零点闭店归一化（M14 · 救活两个「死点」）

根因：parse_poi 的 close_h = hhmm_to_h(close) 不处理跨午夜。18:00-02:00 / 10:00-06:00 这类点 close_h < open_h，被三重判死：

① toptw 预剔除：to_min(close) - dur = -420 - 90 < 0
② toptw 时间窗：lo = to_min(open) = 540 > hi = to_min(close) - dur = -510
③ sequencer：任意到达时刻都满足 t + dur > close_h → 恒报「超出营业时间」

修法：close_h <= open_h 时 +24（00:00 全天点也走这条）。全库 528 点中仅 2 点触发（GZ069 宝业路宵夜街 18:00-02:00、NJ021 1912 街区 17:00-02:00），其余 526 点零影响。归一化后 close_h=26.0，与 day_end 上限共同决定它只能排在当天收尾时段，符合真实语义。

判定特征（已固化为单测）：单测里还原 close_h 后，该点在求解器中「既不入选也不出现在 dropped」——从模型完全消失。这是「死点」区别于「利润权衡剔除」的判据（scripts/test_cross_midnight_close.py，8 组断言含修复前对照）。

新增点位若营业到凌晨，必须靠这个归一化才排得进（KTV 的 06:00 闭店即依赖它）。注意归一化解除的是「绝对不可排」，不等于「必然入选」——GZ069 线上仍未落地，根因已变为提案层不提案（属召回层问题）。

5G · 空档治理与点名召回（M15 · 一次迭代修三个缺陷）

病灶 1 · 日内空档：全量扫描 13 用例 × 全部天数，≥45min 空档共 357min，且逐条核对后全部出现在正餐点之前——旧代码 start = max(t2, ws, p["open_h"]) 把餐厅钉死在 12:00/18:00 整点，10:45 到场也要干等 75min。修＝MEAL_EARLY_TOL_H=1.0（餐窗起点前 1h 内可开吃）+ _fill_wait_with_meal（等待开门的硬空白里先吃饭）+ scan_gaps/_gap_notices（空档分类 wait_open / wait_meal / free 并按天披露）。同扫描 357min → 60min。

病灶 2 · 点名召回：用户点名的点「库与管线都正确，却从不被提案」。三层缺一层就白干：

层位置修法

② 必选与对账forced_ids_for(anchor_poi, grounding)口径＝「需求点名的全量库内点」（named_pois），不是「本次注入了什么」（named_injected）——LLM 恰好自己提案了点名点时后者为空，会既不被列必选、被剔后也不披露；丢失必发 named_lost 对账
③ 下游守门m2_planner._fix_food_detours该函数前提是「咖啡是配套不是目标」，却把 category=food 的目的地型餐饮（莲花岛＝阳澄湖农家乐集群、suburb、dur 2h）当绕路配套剔除。修＝_is_destination_food（郊区／停留 ≥2h／农家乐类名）+ protect（点名点豁免）

病灶 3（顺带挖出）· 19:00 后开门的点结构性不可排：MEAL_BUFFER_MIN=120 把求解 horizon 压到 630min（19:30），GZ066 珠江夜游、GZ069 宝业路一类 18:00 后开门点恒不可行 → 新增 LATE_POINT_MARGIN_MIN=60，按池内最晚需求放宽、上限为真实日窗。

教训：① 「LLM 听话」和「用户要求被满足」是两件事——必须独立对账，不能拿流水线内部记录当口径；② 判断某类目点是「配套」之前，先问它会不会本身就是用户目标（category 是粗标签，food 里既有咖啡馆也有农家乐目的地）；③ 探针要带调用行号（traceback.extract_stack），否则「哪一层改的」只能靠猜；④ 属性方差大的指标（LLM 逐次提案不同）不能作为唯一验证依据，最终要落到确定性单测。守卫 test_gap_manage.py / test_named_inject.py（均含「关掉新参数复现旧缺陷」的对照）。
