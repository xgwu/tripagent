TripAgent 架构设计文档

AI 智能体驱动的多日行程规划系统 · 版本 M8（2026-09-12）· 对应代码 main@c64afb6
一句话架构：LLM 负责它擅长的（用世界知识理解需求、选点、组织体验节奏），确定性系统负责它擅长的（落地校验、约束守护、组合优化）——世界知识主导选点，系统只做落地 + 约束 + 求解。LLM 从不直接决定最终行程；优化器从不用 LLM 修 bug。

1 · 设计哲学与边界划分

传统两种做法都有结构性缺陷：纯 LLM 排程（直接让大模型输出时间表）幻觉不可控、时间/里程约束靠"自觉"；纯算法规划（标签过滤 + 贪心）选点品味差、无法理解"带5岁孩子不要太累"这类软需求。TripAgent 的核心决策是把两者切在正确的层：

职责归属理由
需求理解、城市/天数/日期/酒店解析LLM（llm_extract/llm_clarify）+ 规则兜底自然语言歧义是 LLM 强项，规则只做降级
选什么点（品味层）LLM 世界知识提案，不限制在库内清单库内选点会让行程被 POI 库质量锁死（M1→M7 的核心演进动机）
提案是否真实存在（事实层）确定性落地匹配（四级），绝不信 LLM幻觉结构性归零的关键：LLM 说什么不重要，库里能落地什么才重要
排程顺序、时间轴、里程/闭馆/用餐约束OR-Tools TOPTW 求解 + sequencer 确定性修复组合优化是求解器的领域，LLM 排时间表必然违规
被约束否决后的补救闭环反馈（LLM 重提案）+ 跨天重平衡（确定性局部搜索）LLM 修正"选点被否决"，算法修正"天间错位"，各管各的
最终文案LLM 重生成，但只能基于最终时间轴防"标题有宋城、列表没有宋城"式文案漂移（ee9f1d2 教训）
推论：POI 库的角色从"选点来源"降级为"事实校验层 + 缺口探测器"——未落地清单就是库的质量报告，直接驱动扩库。

5 · 关键机制设计详解

5.1 四级落地匹配（防幻觉的核心）

提案里的每个名称按序通过四级匹配，任何一级命中即算落地；四级全失 → 记入 gaps（不计入落地率惩罚，仅作库缺口信号）：

级别策略成本典型案例
L1 精确归一化后精确等值（去空格/全半角/括号注记）0「宋城·宋城千古情」→ HZ032
L2 分支变体剥除「东/西/北/乐园/度假区」等后缀生成变体再精确匹配0「上海迪士尼度假区」→「上海迪士尼」
L3 包含/模糊双向子串 + 编辑距离模糊0「外滩」→「外滩观景大道」
L4 LLM 辅助未落地清单 + 候选库打包给 LLM 对齐；住宿类库点双侧排除（防把酒店排进行程）1 次调用「武康路梧桐区」→ 武康路·安福路

实测：eval_m7 五城 10 组真实 LLM 提案落地率 10/10 全 100%，其中绝大多数命中 L1/L2——LLM 提案用的是官方名称，落地比想象容易。

5.2 TOPTW 利润函数（选点品味进入数学模型）

profit(p) = main_bonus × is_main + w_rating × rating + w_rank × (n_rank − rank)
主选奖励保证 LLM 主选优先保留；LLM 备选（alternates）与检索邻近备选只带评分/顺位收益进池（低权重），供求解器在时间预算内换点——这是"备选双源"设计：LLM 自备 alternates + 库内地理召回，去相关化防同源幻觉。

forced 集合（酒店锚点等地标）通过利润 +1e6 强制必选；is_full_day（duration_h≥8，如迪士尼）自动独占一天。

5.3 闭环反馈（两个触发点，共享 2 轮预算）

触发点信号动作采纳守卫
① 落地不足gaps 非空 或 落地率 < 0.85未落地清单 + 原因回传 REVISE 重提案修正确实减少未落地/剔除才采纳，否则保留原结果（防震荡）；MAX_REVISE_ROUNDS=2
② 主选被剔mains_dropped 非空（ee9f1d2 补上——此前只看修复链剔除，求解器剔主选从不触发，宋城案例暴露）剔除 POI + "时间预算内无法纳入"原因回传

备选被剔不算触发——备选本来就该被挑拣，闭环只救"LLM 的核心意图被系统否决"。

5.4 跨天重平衡（对标 Google《Optimizing LLM-based trip planning》stage-2）

  • 各日 TOPTW 独立求解后，确定性尝试把 POI 移动到地理更近的日簇（纯算法，0 次 LLM 调用）
  • 接受条件四选全：移动后全行程 0 违规 + 0 修复剔除 + 总里程改善 > 0.5km − 2km 相似度罚分（罚分尊重 LLM 初稿，不无意义搬运）
  • 保护规则：is_full_day 大点与 forced 锚点永不动；供出日至少保留 1 点；移动后整体重求解，主选掉点则整体回滚
  • 指标 n_day_moves 透出——机制只在有真实收益时动作（真实评测中提案聚类良好时为 0）

5.5 文案-时间轴一致性

compose 阶段 4 用 REGEN_PROMPT 对最终时间轴重新生成 theme + reason，prompt 明确约束"只能提到时间轴里实际存在的 POI"（举例：时间轴没有宋城就不能叫宋城怀古）。这是对"提案主题残留被剔 POI"问题的根治（ee9f1d2）；前端 Day 卡、分享 HTML、PNG 长图三处消费同一字段。

5.6 住宿锚点（三级匹配 + 开关化）

用户说"住迪士尼附近"时：L0 库内地标匹配（rating≥4，"迪士尼"直接命中 SH006）→ L1 高德 POI 搜索（含"酒店"关键词过滤）→ L2 裸搜兜底。解析出的地标可注入当日必选（ensure_landmark_in_day_map + forced）；确定性硬保障（anchor_hard_guarantee）做成默认关的开关——世界知识主导原则下，软引导优先，硬保障只在需要时打开。

7 · LLM 交互面与降级矩阵

调用点用途失败降级
llm_extract需求结构化（天数/日期/酒店/同行人）正则规则解析（extract_days/date/hotel）
llm_clarify保守判断是否追问（≤1 问）静默放行直接规划
PROPOSE_PROMPT世界知识提案（主选/备选/主题）离线规则提案（offline_planner）
REVISE_PROMPT闭环修正（未落地/主选被剔回传）保留原结果，gaps 透出为提示
_llm_matchL4 辅助落地未落地计入 gaps（不阻塞管线）
REGEN_PROMPTtheme+reason 重生成沿用提案阶段 theme，reason 置空
原则：任何 LLM 环节失败都不能让管线崩溃——最坏情况退化为"规则解析 + 离线提案 + 纯求解器"，行程仍然成立，只是品味下降。这也是 eval_regression 默认离线跑得通的原因。

8 · 质量保障体系

三层评测
  • 回归闸门：eval_regression 12 用例，离线（mock LLM，秒级）+ --llm 真实全链路双跑，任何 prompt/求解改动必须双绿

  • 多层缓存：llm_cache(7d) / nl_cache / route_cache / photo_cache，重复请求近零成本
  • 幂等 onboarding：脚本全部可重跑
  • 密钥治理：secrets.json gitignore，config.json 进 git（7b207aa）

12 · 已知边界与演进方向（P2）

  • 向量检索匹配层：四级匹配前置 embedding 相似度，进一步压缩 L4 辅助匹配的调用率与延迟
