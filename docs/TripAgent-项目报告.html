一、项目定位与设计哲学

TripAgent 回答一个核心问题：通用大模型（豆包/千问级）的旅行「品味」很好，但直接生成的行程不可行——幻觉地点、营业时间冲突、跨天重复、里程不现实。项目的解法是让 LLM 与优化器各做擅长的事：

世界知识主导选点，确定性系统负责「落地 + 约束 + 求解」。

LLM 凭旅行常识决定「去哪、为什么去」（上海亲子就该想到迪士尼），系统保证行程物理可行（真实路网时间、营业窗口、闭馆日、餐窗、里程预算）且结构最优（OR-Tools TOPTW 排序与可行性）。防幻觉不靠限制提案，而靠落地匹配——未落地的提案自动成为「POI 库缺口采购清单」，反向驱动数据扩容。

v3 的定位微调（M11 忠实执行模式）：随着提案层 prompt 成熟（v7），选点权进一步收归 LLM——TOPTW 从「可以换点」退到「只排序 + 保证可行」。这不是能力削减，而是职责归位：节奏与强度是用户意图，应由理解意图的一方决定；求解器不该用利润函数替用户做减站点决策。求解器仍保留换点能力（配置可回退），并继续负责它最不可替代的两件事：时间窗可行性与顺序最优。

四层防护保证产出质量：

案例 1 · 动物主题行程无动物点（M9）

现象：「带 5 岁孩子去杭州玩 2 天，不要太累，最好有动物或者博物馆」——行程里没有任何动物相关 POI。逐环节重放定位：

环节状态证据
LLM 提案正确Day2 主题「动物王国与运河文化体验」，主选第 1 位=杭州极地海洋公园
落地匹配正确exact 命中 HZ047，11/11 全落地
TOPTW 求解正确Day2 解保留极地海洋公园
修复链剔除亲子里程超预算（>20km/天）剔最远点——海洋公园（萧山 18.8km）与拱宸桥片区（城北）相距 24km+
补位丢主题备选补位只看几何，不保留「动物」需求；库内无第二个轻量动物点

三层修复（8090eb9 / 45dfa4f / 3297ee7 / 580b54d）：数据（杭州库补杭州动物园 HZ056 + 野生动物世界 HZ057，KEYWORD_TAGS 加动物映射）、守门（远郊大点片区守门 + family 档 5h+ 独占日，去掉亲子里程硬上限）、主题保真（补位同主题优先 + _demand_notices 需求丢失检测 + 前端 ⚠️ 徽标）。

案例 2 · 慢节奏档「全链旁路」——一个正则吃掉了整条宽松策略（M12）

现象：「带老人玩 2 天，不要太累」的行程被 TOPTW 塞到 20:30 才收尾、单天 5-7 站。慢节奏档明明已上线，全部宽松规则却像没生效。

根因：SLOW_PACE_RE 当时写作 老人|轮椅|不累|…——「不要太累」不含「不累」这个连续子串（中间隔了「要」和「太」）。正则不匹配 → _slow=False → 慢节奏档整条链路被旁路：prompt 规则、夜间点移除、TOPTW 禁池、MIN_STOPS、提案截断 stops≤4、补强池三重过滤全部失效。

教训（写进项目公约）：慢节奏触发的亲子回归全是离线确定性路径，测不出 LLM 提案链的正则门控——正则改动必须用真实 LLM 实测验证，不能只靠离线回归。

修复后的兜底七处（缺一即漏，因为 evening 点/超员点即使被 prompt 禁止，仍会从 alt 补位/填空/换点/池捞回来）：主选层移除 evening+nightlife 点 / _alt_substitute 跳过夜间备选 + 补位 cap4 / MIN_STOPS 统一 3（2 点实测 13:00 收工偏薄）/ TOPTW 禁池彻底化（邻域池 + LLM alts 都不进池）/ 提案层截断 stops≤4 / 补强池三重过滤 / 站数下限 min_keep=3 防两层闭环里 rebalance 把凑起来的天挪薄。

夜间点判据精准化（报障 11）：poi_db.is_night_only(p) = nightlife 类目 or open_h ≥ 16.5。不能按 best_time=evening 一刀切——外滩（0:00-23:59）/南京路步行街/陆家嘴滨江/山塘街全是全天开放点，误杀曾致上海亲子慢节奏 Day2/Day3 2 站 15:21/14:45 就收工。

案例 3 · 正餐 POI 永远排不进餐窗（M12）

现象：前端长期提示「美食 POI 未能安排进用餐时段」。

根因：_build_timeline 单趟遍历里通用餐块先到先占窗（11:30 占掉午餐窗、17:00 占掉晚餐窗），等遍历到真实正餐 POI 时窗口已被占，只能落进另一个窗或超 MAX_MEAL_WAIT_H → 违规剔除 → 前端提示。教训：候补块与真实 POI 之间必须有显式优先权——真实 POI 优先。

修复：_assign_food_windows 统一分配（午市优先 / 同窗顺延 / 不可用窗不分配）+ pending_food_win 认领计数让通用餐块让位；残余形态由 food_window_plan + _reconcile_food_windows（主选层提前降级、不回填 alt_map、写 grounding.food_demoted）+ PROPOSE_PROMPT v7（正餐 ≤2 且午晚各一家、默认 1 家）解决。线上美食剔除 4 → 0。

餐窗补齐三件套（报障 10/12）：MEAL_LEAD_H=0.5 通用化（到达距饭点 ≤30min 先吃再逛）、游完就地补餐、MEAL_EXIT_GRACE_H=0.75 窗尾宽限 + MEAL_END_LEAD_H=1.5 收尾晚餐提前量——专治 2~4h 游览横跨餐窗的盲区（上博 10:15–13:15 出来已过窗尾，「途中解决」把午餐吞掉）。

教训：确定性 gate 必须挂在循环/重试链路的每一个入口——挂在第一轮漏了第二轮等于没挂；提前降级优于事后剔除 + 提示。

案例 4 · 两个「死点」：自入库起从未能被排进任何行程（M14）

现象：广州宝业路宵夜街（18:00-02:00）与南京 1912 街区（17:00-02:00）两个 nightlife 点，上线以来一次都没进过任何行程。

根因：parse_poi 的 close_h = hhmm_to_h(close) 不处理跨午夜——18:00-02:00 被解析成 open_h=18.0, close_h=2.0，从而被三重判死：

① toptw 预剔除：to_min(close) - dur = -420 - 90 < 0        → 建模前就出池
② toptw 时间窗：lo = to_min(open) = 540  >  hi = -510      → 窗口为空
③ sequencer：任意到达时刻都满足 t + dur > close_h          → 恒报「超出营业时间」

修法：close_h <= open_h 时 +24 归一（02:00 → 26.0）。全库 528 点中仅这 2 点触发，其余 526 点零影响；归一化后与 day_end 上限共同决定它只能排在当天收尾时段，符合真实语义。

判定特征（固化为单测断言）：单测里还原 close_h 后，该点在求解器中「既不入选也不出现在 dropped」——从模型完全消失。这是「死点」区别于「利润权衡剔除」的判据，已固化在 scripts/test_cross_midnight_close.py（8 组断言，含修复前对照）。

运行时验证：parse_poi(GZ069) 实测 close_h=26.0 ✅。GZ069 仍未出现在行程里，但根因已不同——现在是提案层 LLM 不提案它（toptw_dropped 为空 = 从未进求解器），属召回层问题，与修复前「进了池也被判死」是两回事。

案例 5 · 骑行主题日被「拆杀」（M12）

现象：苏州环太湖骑行主题日，提案完全正确，落地后湖点被拆散到不同天，行程跑偏古城。

根因链：LLM 提案正确 → _far_big_point_regroup 把环湖线点位间 17-26km 判为「错配」强制挪到邻天（FAR_BIG_KM=12 / SPREAD_KM=10 对环湖线本身失效——湖线点位天然相距十几公里）→ 邻天市区动线 TOPTW 把湖点团灭。

修复：非 family 严格档时，被判错配的点全部 >12km 远郊 → 环湖/海岛主题日豁免不拆；同时 CYCLE_MAX_KM 6→8km（6km 会在古城尺度误伤：虎丘→双塔 6.2km 被标车程而文案说骑行），修 _hop_label 与文案一致性。

验证：回归 14/14；双日冒烟 Day1 保留 4 湖点整编制 + Day2 古城独立。

七、关键技术决策

1. 为什么不直接让大模型排行程

直接生成的行程有三类结构性问题：地点幻觉（不存在/已关闭的店）、时间不可行（跨城 30 分钟「顺路」）、约束盲区（闭馆日/餐窗/跨天重复）。M1 已量化验证：候选卡片约束下 LLM 幻觉归零，但选点品味被库限制；M7 把品味还给它，可行性交还给求解器。

2. 利润函数而非规则堆叠

TOPTW 利润 = 主选标记 600 + 评分×60 + LLM 顺位×15，软时间窗每偏差 1 分钟罚 5 分（封顶 60min）。参数扫描发现 MAIN_BONUS 300~1000 结果完全一致，SOFT_W=5 最优——调参用数据说话。点级需求加成（湖偏好）走 _bonus 字段，必须 int（OR-Tools 罚分要求 int64）。

3. 闭环只修「世界知识被否决」

备选被求解器剔除是正常行为，不触发闭环；主选（LLM 世界知识的判断）被时间预算否决才是需要反馈的信号（宋城/迪士尼案例）。修正采纳有防震荡守卫：新提案剔除数必须减少才采纳。

4. 确定性算法优先于 LLM 调用

跨天重平衡用纯局部搜索（0 LLM 成本）；备选确定性补位优先于 LLM 兜底；提案级缓存直接跳过 A 阶段。这与 Google 论文的 stage-2 set packing 局部搜索同构。

5. 文案与时间轴强一致

主题和理由都基于最终时间轴重生成（曾出现「标题有宋城、列表没有宋城」的教训），REGEN_PROMPT 明确禁止提及时间轴外地点；排程事实（闭馆日）注入 prompt，矛盾 tips 确定性剔除。

6. 守门在事前，而非修复链事后

动物主题案例的教训：依赖修复链按日里程事后剔点，会在「几何不可行」时误杀世界知识主选且丢失需求主题。正确姿势是提案层守门（求解前把错配点排好）+ 补位保主题 + 丢失显式通知——三层各司其职，修复链只处理真正的尾部情况。

7. 选点权收归提案层（M11 忠实执行）v3 新增

M7 时代求解器有权在利润函数下换点，导致「用户说慢节奏、求解器按利润塞满」这类意图与优化目标打架。M11 起默认忠实执行：TOPTW 只排序，主选锁定，点数上限由提案层承诺。代价是失去「库内自由发挥」的补偿能力，收益是行为可解释——剔除只剩一种原因（时间装不下），剔除记录口径也据此分流。配置 toptw_faithful_mode 可回退。

8. 判据失败先问「数据到位了吗」v3 新增

报障 16（city_meta 没下发 category → 前端用餐图标判据恒为假）、报障 17（server.py 城市映射表漏注册广州 → 全城图片 400）同族：判据依赖的字段/条目要先验证真的存在，再怀疑逻辑。另一条同族教训是「查数据缺失先排除自己查错键名」（dur vs duration_h 曾致误判）。

9. 多副本注册表必须有机守v3 新增

城市元数据散落 ≥5 处（server.CITIES / _ID_PREFIX_CITY / _CITYCODE / fetch_poi_photos.CITYCODE / expand_travel_cache.CITIES / 评测 CASES），改一处必漏——广州开城时正因漏改 server.py 副本而全城不出图。scripts/test_city_registry.py 现以「8 城 × 4 张表 + 前缀识别」硬断言守卫，开城/加城必跑。
