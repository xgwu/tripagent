一、项目定位与设计哲学

TripAgent 回答一个核心问题：通用大模型（豆包/千问级）的旅行「品味」很好，但直接生成的行程不可行——幻觉地点、营业时间冲突、跨天重复、里程不现实。项目的解法是让 LLM 与优化器各做擅长的事：

世界知识主导选点，确定性系统负责「落地 + 约束 + 求解」。

LLM 凭旅行常识决定「去哪、为什么去」（上海亲子就该想到迪士尼），系统保证行程物理可行（真实路网时间、营业窗口、闭馆日、餐窗、里程预算）且结构最优（OR-Tools TOPTW 利润最大化）。防幻觉不靠限制提案，而靠落地匹配——未落地的提案自动成为「POI 库缺口采购清单」，反向驱动数据扩容。

二、核心管线（M7 经验提案模式）

0 · 多轮澄清LLM 保守判断需求缺失（天数/同行人/歧义），至多追问一问，选项卡片交互
→
A · 世界知识提案LLM 自由生成多日行程：主选 + note + alternates + 招牌体验规则
→
B · 落地匹配四级匹配回库：精确 → 包含 → 模糊(difflib≥0.62) → LLM 辅助；失败记入库缺口
→
C · TOPTW 求解OR-Tools 逐日求解：营业时间窗 + 酒店锚点 + 闭馆硬过滤 + 利润函数
→
D · 闭环与文案跨天重平衡 → 主选被剔/缺口回传 LLM 修正（≤2轮）→ 文案对齐最终时间轴

三层防护保证产出质量：

  • 提案层：招牌体验规则（亲子→迪士尼）、全天大点独占日、亲子里程预算 20km/天、雨天室内引导；
  • 求解层：主选高利润 + LLM 备选低权重 + 地理邻近检索备选（双源）入池，不可行按利润权衡换点；
  • 闭环层：落地缺口/落地率<85%/主选被剔 ≥2 处 → 带原因回传修正再求解（上限 2 轮，防震荡守卫）。

五、关键技术决策

1. 为什么不直接让大模型排行程

直接生成的行程有三类结构性问题：地点幻觉（不存在/已关闭的店）、时间不可行（跨城 30 分钟「顺路」）、约束盲区（闭馆日/餐窗/跨天重复）。M1 已量化验证：候选卡片约束下 LLM 幻觉归零，但选点品味被库限制；M7 把品味还给它，可行性交还给求解器。

2. 利润函数而非规则堆叠

TOPTW 利润 = 主选标记 1000 + 评分×60 + LLM 顺位×15，软时间窗每偏差 1 分钟罚 5 分。参数扫描发现 MAIN_BONUS 300~1000 结果完全一致（主选本就 28/28 保留），SOFT_W=5 最优——调参用数据说话。

3. 闭环只修「世界知识被否决」

备选被求解器剔除是正常行为，不触发闭环；主选（LLM 世界知识的判断）被时间预算否决才是需要反馈的信号（宋城/迪士尼案例）。修正采纳有防震荡守卫：新提案剔除数必须减少才采纳。

4. 确定性算法优先于 LLM 调用

跨天重平衡用纯局部搜索（0 LLM 成本）：移动 POI 到更近日簇，接受条件为 0 违规 + 0 修复剔除 + 总里程改善 >0.5km − 2km 相似度罚分；全天大点与锚点永不动。这与 Google 论文的 stage-2 set packing 局部搜索同构。

5. 文案与时间轴强一致

主题和理由都基于最终时间轴重生成（曾出现「标题有宋城、列表没有宋城」的教训），REGEN_PROMPT 明确禁止提及时间轴外地点。
